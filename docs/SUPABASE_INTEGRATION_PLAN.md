# خطة تأسيس Supabase — سوق إب

**الحالة:** تأسيس معماري فقط؛ لا توجد كتابة إلى قاعدة Supabase حتى اجتياز بوابة فحص المخطط والصلاحيات.  
**مرجع المنتج:** ملف PDR الكامل في Drive، إصدار PDR-HLM-ENCYCLOPEDIA-2026-V10.0.  
**المشروع المتصل:** `yemen-commerce-ai` — `fruuvdvyyueobgpxsder` — المنطقة `ap-northeast-2`.

## 1. قرار البنية

- الهدف طويل المدى: PostgreSQL/PostGIS قاعدة البيانات التشغيلية الأساسية، بما يتوافق مع ADR-008 في PDR.
- Cloudflare Workers تبقى طبقة API/edge والحماية والتخزين المؤقت، ولا تتحول D1 إلى محرك معاملات أو دفتر مالي.
- D1 الحالية تبقى مصدر تشغيل الكتالوج الحالي إلى أن تُنفّذ عملية ترحيل مضبوطة ومتحقق منها؛ يمنع تشغيل كتابة مزدوجة بين D1 وSupabase.
- لا ننقل سجلات دليل المنشآت القديمة أو أرشيف Google Maps ضمن تأسيس Supabase. يظل تحقق الأرشيف مؤجلًا بناءً على قرار المنتج.
- لا نستخدم المفتاح السري أو service-role في المتصفح أو ملفات Git. أي عمليات امتياز أعلى يجب أن تكون داخل خدمة خادمية/Edge Function مع سياسات وصول واضحة.

## 2. ما تم التحقق منه

- اتصال Supabase يعرض منظمة `mhommdkuyr's Org` ومشروعًا واحدًا باسم `yemen-commerce-ai`.
- المشروع يستخدم PostgreSQL 17.6.1؛ مرجع PDR يذكر PostgreSQL 16 + PostGIS 3.4، لذا يجب اختبار التوافق على الإصدار الفعلي وعدم فرض downgrade.
- عنوان المشروع: `https://fruuvdvyyueobgpxsder.supabase.co`.
- المشروع كان `INACTIVE` عند بدء المهمة، وتم طلب استعادته. الحالة الأخيرة التي رجعت من Management API هي `COMING_UP`؛ لذلك لم يكن محرك قاعدة البيانات متاحًا بعد للفحص.
- فشل `list_tables` برسالة أن قاعدة البيانات غير متاحة؛ لا يوجد حتى الآن إثبات لوجود أو غياب أي جدول في قاعدة Supabase.
- لم تُنشأ جداول أو سياسات أو دوال، ولم تُكتب أو تُحذف أي بيانات.

## 3. ملاحظة تدقيق مهمة في ملف PDR

يحدد PDR نطاقًا واسعًا: 58 شاشة، 42 جدولًا، و65 عقد API، ويقرر PostgreSQL/PostGIS قاعدة أساسية. لكن مقاطع DDL المدرجة في قاموس البيانات تكرر قالبًا عامًا متطابقًا تقريبًا لعدة جداول (`id`, `tenant_city_code`, `entity_status`, `h3_index_res8`, `payload_metadata`, `vector_clock`, timestamps) ولا تمثل وحدها تعريفًا كافيًا لحقول كل كيان أو علاقاته التشغيلية. لذلك لا يجوز إنشاء 42 جدولًا آليًا من تلك القوالب أو اعتبارها مخططًا إنتاجيًا كاملًا. يجب استخلاص نموذج كل نطاق من مواصفات الشاشة وعقود API وأمثلة الخدمات، ثم التحقق منه باختبارات.

## 4. مراحل التأسيس المقترحة

### المرحلة A — فحص القاعدة (قراءة فقط)
1. التأكد من أن حالة المشروع أصبحت `ACTIVE`.
2. جرد المخططات والجداول والأعمدة والمفاتيح الأجنبية والفهارس والهجرات.
3. فحص امتدادات PostgreSQL، وبالأخص PostGIS، ثم التحقق من إصدارها.
4. جرد سياسات RLS والمنح العامة وواجهات Data API والدوال والمشغلات.
5. تشغيل Supabase Security وPerformance Advisors وتسجيل النتائج قبل التغيير.

### المرحلة B — نموذج المجال الأولي
بعد إتمام الجرد فقط، تصميم أول مجموعة متوافقة مع التنفيذ الحالي وPDR:
- هوية المستخدمين وربطها بـ Supabase Auth دون نسخ كلمات المرور.
- ملفات المتاجر وملكية التاجر وحالة المراجعة.
- كتالوج المنتجات وSKU والمتغيرات.
- المخزون وأسعار المتجر.
- مساهمات المتاجر/المنتجات وقائمة المراجعة وسجل التدقيق.
- دليل الأماكن ككيان مستقل عن المتاجر التجارية المعتمدة.

يجب اعتماد أنواع UUID والعلاقات والفهارس المكانية بدقة. لا يُنشأ مخزون أو طلب شراء من مجرد وجود سجل دليل.

### المرحلة C — الأمن وRLS
- تفعيل RLS على كل جدول في `public` أو أي مخطط مكشوف عبر Data API.
- سياسة عامة للقراءة فقط للصفوف المنشورة/المعتمدة، إن تطلبت الواجهة ذلك.
- سياسات `authenticated` مرتبطة بملكية السجل أو عضوية الدور؛ لا تكفي عبارة `TO authenticated` وحدها.
- صلاحيات الإدارة والتعديل لا تستند إلى `user_metadata` القابل لتعديل المستخدم.
- لا تستخدم `SECURITY DEFINER` كحل لتجاوز رفض الصلاحيات.
- لا تكشف `service_role` أو secret key في JavaScript العميل أو GitHub.

### المرحلة D — الربط التدريجي
- إنشاء API خادمي/Edge Function أو Worker adapter واحد يتعامل مع PostgreSQL.
- تثبيت عقد الاستجابة الحالية حتى لا تتعطل واجهة العميل والتاجر.
- اختبار قراءة الكتالوج، تقديم المساهمات، منع تكرار الطلبات، ومراجعة الإدارة.
- تشغيل Shadow reads ومقارنة النتائج مع D1 قبل أي تحويل للقراءة.
- تحويل الكتابة والقراءة بعد اختبار النسخ الاحتياطي والاسترجاع وخطة rollback فقط.

### المرحلة E — الترحيل
- وضع خريطة حقل-إلى-حقل بين D1 وPostgreSQL.
- أخذ snapshot وchecksum لكل دفعة، مع سجل استئناف.
- عدم نقل سجلات غير موثقة إلى حالة منشورة.
- عدم استيراد ملف 16,441 الخام أو أرشيف Google Maps المؤجل.
- بعد المطابقة فقط، تحويل API إلى Supabase وإبقاء D1 للقراءة/الرجوع خلال فترة مراقبة محددة.

## 5. ضوابط التغيير

- جميع تغييرات المخطط تبدأ بملفات migration مراجعة واختبارات؛ لا تغييرات مرتجلة في الإنتاج.
- لا يتم تطبيق Migration على قاعدة حية قبل مراجعة SQL والآثار الأمنية والتوافق.
- لا تنشأ مشاريع أو فروع Supabase إضافية دون عرض تكلفتها والحصول على موافقة المستخدم.
- لا تُفعّل OTP أو الدفع أو Escrow أو الطلبات الحقيقية كواجهات شكلية؛ لكل منها بوابة تشغيل ومزود/سياسة محلية.
- أي جداول جديدة في Supabase يجب ألا تفترض أنها مكشوفة تلقائيًا عبر Data API؛ من 30 أكتوبر 2026 أصبح التعريض التلقائي للجداول الجديدة مقيدًا افتراضيًا، ويجب تحديد المنح وRLS صراحة.

## 6. الحالة الحالية والخطوة التالية

**المتوقف حاليًا:** انتظار اكتمال استعادة مشروع Supabase حتى يصبح PostgreSQL قابلًا للفحص.  
**المتاح الآن:** مستودع التطبيق الحالي وWorker/D1 ووثائق مواءمة PDR.  
**ممنوع حتى اكتمال الفحص:** تطبيق أي DDL أو نقل بيانات أو تحويل مصدر الحقيقة.

بعد ظهور حالة `ACTIVE`، تكون أول خطوة قراءة فقط: جرد الجداول والامتدادات والهجرات وRLS/Advisors. لا يكتب هذا المستند أي شيء إلى قاعدة البيانات.
