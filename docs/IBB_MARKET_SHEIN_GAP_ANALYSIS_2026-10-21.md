## 1. القرار التنفيذي

إب ماركت يملك أساسًا مفيدًا: واجهة عربية RTL، قائمة أسماء محلية، بحث بسيط، خريطة قابلة للفتح، وبعض نماذج تجربة المستخدم. لكنه حاليًا **دليل أسماء ثابت وليس سوقًا إلكترونية متعددة البائعين**. مقارنة SHEIN هدفها تحديد الأنظمة الناقصة وترتيبها، وليست إثبات أن تقليد واجهته وحده سينشئ سوقًا ناجحًا.

**النتيجة:** الفكرة والواجهة الأولية تصلحان للاستمرار، لكن النتيجة ليست مرضية بعد بوصفها منصة تجارة كاملة. الأولوية الصحيحة هي الثقة والبيانات المشتركة وتوثيق المتاجر أولًا، ثم كتالوج منتجات حقيقي وبحث موثوق، وبعد ذلك فقط البحث بالصورة والمعاملات والدفع والتوصيل.

## 2. خط الأساس الحالي كما يظهر في الشيفرة والوثائق

| المساحة | الموجود حاليًا | الحالة |
|---|---|---|
| واجهة المستخدم | صفحة رئيسية عربية RTL مع تبويب للخريطة وتجاوب للهاتف | موجود |
| دليل المنشآت | 11,060 سلسلة نصية مستوردة، مقسمة إلى 23 ملف JSON وفق README والفهرس | موجود؛ الاسم فقط ولا يعني أن كل سجل متجر عامل |
| البحث | تطبيع نص عربي ومطابقة substring محلية | موجود، محدود |
| التصفية والترقيم | الكل/محلي/متابعة/له موقع محلي؛ 30 نتيجة ثم عرض المزيد | موجود محليًا |
| ملف المتجر | نافذة تفاصيل مبنية من اسم؛ حالة التوثيق غير مثبتة | هيكل تجريبي |
| تحديد الموقع | دبوس Leaflet يدوي وإحداثيات محلية | موجود محليًا، غير موثّق |
| المنتجات | إضافة اسم/وصف/سعر اختياري وصورة URL للاختبار | محلي فقط |
| المتابعة والإعجابات والمطالبة بالملكية | localStorage | محلي فقط؛ لا يصل إلى تاجر أو إدارة |
| البحث بالصورة | الزر معطّل وموسوم «قريبًا» | غير منفّذ؛ السلوك الحالي صريح وصحيح |
| مساعد البحث | مطابقة نصية في بيانات متاحة محليًا | ليس نموذجًا ذكيًا متصلًا بالمخزون |
| الحسابات والصلاحيات | غير موجودة كمنظومة مشتركة في الواجهة والمستودع | فجوة تأسيسية |
| نشر المنتجات ومراجعتها | لا يوجد تدفق مشترك موثق للمتجر/المشرف | فجوة تأسيسية |
| المخزون والطلبات والدفع والتوصيل | لا يوجد مسار تجارة متكامل في الواجهة الحالية | غير منفّذ |
| البنية الخلفية | يذكر README واجهة Worker، لكن مصدرها غير موجود في شجرة المستودع المفحوصة | لم يتم تدقيق تنفيذها؛ لا نفترض قدراتها |
| اختبارات الجودة | يوجد `scripts/validate.mjs` لفحص البيانات وبنية JavaScript وPWA | مفيد، لكنه ليس اختبار رحلة مستخدم كاملة |
| ملفات PWA | manifest وservice worker موجودان | أساس PWA؛ ليس دليلًا على نجاح جميع حالات العمل دون اتصال |

**ملاحظة فنية للمتابعة:** يستخدم `index.html` مرجعًا إلى `./cloud-catalog.js`، لكن اسم هذا الملف لم يظهر في شجرة الملفات التي فُحصت في هذا التدقيق. يجب التحقق من وجوده في نسخة النشر أو من أن الصفحة تتحمل غيابه بأمان قبل اعتماد اختبار التشغيل؛ هذه ملاحظة تحقق وليست إعلانًا مؤكدًا بأن الصفحة تتعطل.

## 3. مصفوفة الفجوات حسب رحلة الاستخدام

| رحلة/نظام | مرجع النمط التجاري | حالة إب ماركت | الأولوية | معيار القبول |
|---|---|---|---|---|
| اكتشاف المتاجر | تصنيفات وبطاقات ومناطق ترويج | أسماء بلا تصنيف موثوق أو محتوى غني | P1 | كل نتيجة تحمل مصدرًا وحالة توثيق؛ لا تظهر أقسام فارغة كأنها محتوى حقيقي |
| البحث النصي | استرجاع/تصفية كتالوج وفلاتر | مطابقة نص اسم فقط | P1 | البحث في اسم المتجر والاسم البديل والحي والتصنيف والمنتج والوصف ضمن صلاحيات النشر |

| مطالبة المالك | فصل الادعاء عن التحقق | claim محفوظ محليًا | P1 | إثبات تواصل ثم مراجعة ملكية؛ النزاع أو الرفض موثق وسبب القرار متاح |
| كتالوج المنتج | بيانات صنف ونسخ/متغيرات ومراجعة | منتجات محلية بسيطة | P1 | المنتج والمتغير والسعر والمخزون كيانات منفصلة؛ لا يظهر المنتج قبل تحقق صلاحية الناشر ومراجعة المحتوى |
| تحديث السعر والمخزون | تحديثات ذات وقت ومصدر | لا توجد حالة مخزون مشتركة | P1 | لكل عرض سعر ومخزون `updated_at` ومصدر؛ تعرض الواجهة تقادم البيانات |
| الصور | رفع محمي، نسخ مصغرة ومراجعة | URL خارجي في تجربة محلية | P1 | رفع مؤمن للخادم/التخزين، فحص نوع وحجم الملف، معالجة، حذف وتدقيق؛ لا أسرار في المتصفح |
| البحث بالصورة | مدخل كاميرا/ألبوم واسترجاع بصري | معطّل | P2 | اختبارات دقة top-k، حد ثقة، سلوك «لا تطابق»، سياسة احتفاظ بالصورة |
| المتابعة والإعجاب | ارتباط بحساب وخصوصية | localStorage | P2 | مزامنة بين جهازين بعد تسجيل الدخول؛ العدادات الخاصة مخفية افتراضيًا |
| التقييمات/المراجعات | مراجعات مرتبطة بتجربة حقيقية وسياسات إساءة الاستخدام | غير موجودة كخاصية مشتركة | P2 | مراجعة من مصدر صالح، إبلاغ، تعديل/إخفاء موثق، ومكافحة السبام |
| المساعدة الذكية | إرشاد مستند إلى بيانات موثوقة | مطابقة نص محلية | P2 | الإجابة تسند الأسعار/التوفر/المكان إلى مصدر وتاريخ؛ وإلا تقول إن البيانات غير متاحة |
| الإعلانات | ترويج موسوم وملائم للسياق | حيز إعلاني فارغ | P3 بعد الثقة | لا يظهر الإعلان إلا إذا كان مفعّلًا وملائمًا؛ ووسم «إعلان ممول» واضح وتسجيل انطباعات/نقرات داخلي |
| السلة والطلبات | تدفق موحّد للشراء والمخزون والتسليم | غير موجود | P3 بعد جاهزية التشغيل | لا ينشأ طلب مكرر عند إعادة المحاولة؛ حالات الطلب والشحنة والدفع قابلة للتدقيق |
| الدفع والتوصيل | مزودون وقواعد تشغيل محلية | غير موجود | P3 بعد التحقق المحلي | مزود متاح قانونيًا وتقنيًا في اليمن، مع سياسة استرداد وتسوية وحساب توصيل مثبت |
| لوحة الإدارة | مراجعة متاجر ومنتجات وشكاوى | غير موجودة في المستودع المفحوص | P1 | صلاحية أدمن محدودة، سبب القرار، سجل تدقيق، مسار استئناف وحظر |
| التشغيل والنشر | مراقبة وتشخيص وتراجع آمن | GH Pages + Worker مذكوران بالوثائق | P1 | اختبار شبكة هاتف وWi-Fi، مراقبة أخطاء، سياسة أسرار، نسخ احتياطي وتوثيق الاستعادة |

## 4. البنية المستهدفة المقترحة

### 4.1 فصل طبقات النظام

- **واجهة عامة (PWA):** دليل المتاجر والمنتجات، الصفحات العامة، البحث، الخريطة، حالة البيانات، وصفحات المساعدة.
- **واجهة تاجر:** طلب التحقق، بيانات المتجر، المنتجات والمتغيرات، السعر والمخزون، الطلبات، البلاغات، ومؤشرات بسيطة.
- **واجهة إدارة:** مراجعة طلبات التوثيق، فض النزاعات، مراجعة المنتجات، البلاغات، إدارة المحتوى والإعلانات، وسجل التدقيق.
- **API خلفية:** تحقق الهوية والجلسة والصلاحيات، التحقق من المخططات، حدود الطلب، معالجة الصور، البحث وإدارة حالات الأعمال.
- **قاعدة بيانات مشتركة:** PostgreSQL أو خدمة PostgreSQL مُدارة مناسبة، مع migrations واختبارات وترحيل ونسخ احتياطي.
- **تخزين الوسائط:** مساحة ملفات منفصلة بصلاحيات واضحة؛ الصور الأصلية والمصغرات وبصمات المحتوى، مع حد للحجم وسياسة حذف.
- **مهام خلفية:** معالجة الصور والفهرسة واستخراج OCR/CSV ومزامنة الفهرس بعد تحديث السجل، دون جعل الواجهة تنتظر كل مهمة طويلة.
- **الرصد:** تسجيل أخطاء وقياس زمن API وعدد نتائج البحث وأسباب فشل الرفع؛ مع منع تسجيل كلمات المرور ورموز الجلسات ووثائق الهوية.

لا يكفي وجود عنوان Worker وحده لإثبات أن هذه الطبقات موجودة. يجب فحص مستودع الخادم وإعداداته واختبار كل تدفق؛ لا ينبغي وضع مفاتيح سرية أو صلاحيات إدارية في ملفات الواجهة الأمامية.

### 4.2 نموذج بيانات أولي

| الكيان | حقول أساسية مقترحة | ضوابط مهمة |
|---|---|---|
| `users` | id، اسم عرض، هاتف/بريد موثق، role، حالة الحساب | لا تخزّن كلمة مرور صريحة؛ أقل صلاحية لازمة |
| `stores` | id، slug، اسم قانوني/تجاري، وصف، تصنيف، status، created_by | الاسم ليس إثبات ملكية |
| `store_locations` | store_id، lat/lng، عنوان/حي، source، accuracy، verified_at | مصدر وتاريخ التحقق منفصلان عن الاسم |
| `store_claims` | store_id، claimant_user_id، evidence_status، review_state، decision_reason | مستندات خاصة ومحدودة الوصول |
| `store_memberships` | store_id، user_id، role، status | لا يمكن لحساب تعديل متجر غير مخوّل له |
| `products` | id، store_id، name، description، category_id، publication_state | draft/pending/approved/rejected/paused/archived |
| `product_variants` | id، product_id، sku، options JSON مضبوط، barcode اختياري | لا تعتمد على الاسم كمفتاح فريد |
| `offers` | variant_id، price، currency، valid_from، source | سجل تاريخي للسعر بدل الاستبدال الصامت |
| `inventory` | variant_id، quantity/availability، location_id، updated_at | التحقق يتم على الخادم، مع سجل تغييرات |
| `media_assets` | id، owner_id، storage_key، mime، bytes، hash، moderation_state | تحقق من النوع والحجم؛ لا تعرض key خاصًا |
| `follows` | user_id، store_id، created_at | unique(user_id, store_id)، خاصة افتراضيًا |
| `reviews` | user_id، store/product_id، rating، text، state | بلاغات، منع تكرار وإساءة استخدام |
| `orders/order_items` | id، buyer، store، state، totals، address snapshot، idempotency key | لا تُفعّل قبل جاهزية الدفع والتوصيل |
| `order_events` | order_id، old/new state، actor، timestamp | تاريخ حالة لا يمحى |
| `verification_events` | entity_id، reviewer، decision، reason، timestamp | سجل تدقيق قابل للمراجعة |
| `search_events` | query features مختزلة، results ids، clicks، latency | تقليل البيانات وحظر بيانات حساسة |

يمكن بدء التنفيذ بمجموعة أصغر من هذه الجداول، لكن يجب تثبيت حدود الكيانات وصلاحياتها منذ البداية. لا داعي لإنشاء كل نظام الطلبات قبل إنهاء قواعد المتاجر والمنتجات.

### 4.3 واجهات API قابلة للتقسيم

هذه أمثلة لعقد API مقترح، وليست عناوين موجودة حاليًا:

- `GET /api/v1/stores?query=&category=&area=&verified=&cursor=`
- `GET /api/v1/stores/{storeId}`
- `POST /api/v1/store-claims` — إنشاء مطالبة تتطلب جلسة وصلاحية.
- `GET /api/v1/me/store-claims` — حالة المطالبات الخاصة بصاحبها.
- `POST /api/v1/merchant/products` — إنشاء مسودة فقط.
- `PATCH /api/v1/merchant/products/{id}` — لا يقبل التعديل دون عضوية مناسبة.
- `POST /api/v1/merchant/products/{id}/submit` — إرسال للمراجعة.
- `GET /api/v1/search?q=&type=&filters=&sort=&cursor=`
- `POST /api/v1/search/image` — مستقبلًا؛ رفع مؤقت محكوم وسياسة حذف.
- `POST /api/v1/media/uploads` — جلسة رفع مؤقتة بتخويل وحدود.
- `GET /api/v1/health` — health check فقط، ولا يكشف إعدادات أو أسرارًا.

كل عملية كتابة تحتاج تحققًا على الخادم، وتسجيل من نفّذ التغيير، ورسائل خطأ لا تسرب معلومات، وحدودًا للطلبات. يجب تصميم API بما يناسب بيئة النشر الفعلية بدل نسخ أسماء المسارات دون تنفيذ.

## 5. محرك البحث المقترح لإب ماركت

### المرحلة الأولى: بحث نصي متين قبل الذكاء الاصطناعي

1. الاحتفاظ بالنص الأصلي للعرض وعدم استبداله بالنص المطبّع.
2. توليد حقول مطبّعة للفهرسة: Unicode NFKC، إزالة التشكيل والتطويل، توحيد المسافات، معالجة اختلافات الألف والياء، وقاموس مرادفات مكتوب ومراجع محليًا.
3. فهرسة اسم المتجر وأسماءه البديلة والتصنيف والحي والمعلم القريب، ثم اسم المنتج والوصف والسمة المتاحة عند بناء الكتالوج.
4. تصنيف نتيجة البحث حسب نوع الكيان: متجر، منتج، خدمة أو معلم. لا تخلط كل النتائج في قائمة مبهمة.
5. ترتيب قابل للتفسير يبدأ بالتطابق الدقيق/العبارة ثم تطابق الكلمات والمرادفات؛ وتطبيق فلاتر التوفر/التصنيف/المنطقة قبل الترتيب النهائي حيث يلزم.
6. إرجاع نتائج مع cursor وتحديد حد للنتائج بدلاً من إرسال كل الكتالوج إلى الهاتف.
7. إضافة مجموعة اختبارات عربية تضم أسماء حقيقية عامة وتهجئات بديلة وأخطاء إملائية شائعة؛ قياس Precision@k وRecall@k ومعدل «لا نتائج» قبل اعتماد أي وزن.
8. توفير «لم نعثر على نتيجة موثوقة» بدل إظهار نتيجة عشوائية أو اختلاق وجود المنتج.

### المرحلة الثانية: بحث هجين عند توفر بيانات حقيقية

بعد وجود عدد كافٍ من منتجات موثقة، يمكن دمج بحث نصي تقليدي مع استرجاع دلالي (embeddings)، ثم مزج النتائج وإعادة ترتيبها. يجب حفظ إصدار نموذج الفهرسة وتحديث embeddings عند تغيّر الصور أو المنتج، ومراقبة نتائج البحث العربية محليًا. لا يمكن قياس جدوى embeddings من مجرد قائمة أسماء مستوردة.

### المرحلة الثالثة: البحث بالصورة

- رفع الصور عبر خادم يحترم الحدود ويزيل EXIF غير اللازم.
- إنشاء embeddings لصور المنتجات المنشورة بموافقة أصحابها.
- فهرس متجهي يربط كل نتيجة بمعرف المنتج والمتغير.
- استرجاع أفضل المرشحين، ثم ترتيبهم بناء على تشابه الصورة وتصنيف المنتج ونصه وحالة النشر والتوفر وتاريخ تحديث المخزون.
- إظهار درجة ثقة/مؤشرات مطابقة، وإتاحة إعادة البحث بالنص أو تغيير الصورة.
- قياس جودة البحث من مجموعة اختبار مصرح بها، وتقليل احتفاظ صورة المستخدم وحذفها حسب السياسة.
- منع إرجاع نتائج من مسودات أو منتجات معلّقة أو متاجر موقوفة.

يجب ألا يكون هناك ادعاء بأن «البحث بالصورة يعمل» حتى تنجح اختبارات الرفع والفهرسة والاسترجاع والعرض على جهاز حقيقي.

## 6. تسجيل التاجر والتحقق منه

### رحلة مقترحة

1. **إنشاء حساب المستخدم:** تحقق من وسيلة التواصل بواسطة مزود متاح، مع حماية من تكرار المحاولات.
2. **اقتراح متجر أو المطالبة بمتجر موجود:** إذا كان اسم الدليل موجودًا، تبدأ مطالبة ملكية بدل نسخ متجر ثانٍ.
3. **إكمال البيانات العامة:** الاسم، الفئة، الهاتف التجاري/قناة التواصل، الموقع على الخريطة، الحي وساعات العمل عند تأكيدها.
4. **تأكيد الاتصال:** رمز مؤقت من مزود تم التحقق من توفره وتكلفته محليًا؛ لا نفترض أن SMS أو WhatsApp verification متاحان دون مراجعة.
5. **تقديم أدلة الملكية عند الحاجة:** في مخزن خاص ومشفّر وبصلاحية مراجعين محددة؛ لا تحفظها في public bucket ولا ترسلها إلى النموذج اللغوي.
6. **مراجعة بشرية:** قبول/رفض مع سبب؛ التعامل مع أسماء الفروع والنشاط التجاري الملتبس دون دمج تلقائي.
7. **تفعيل صلاحيات التاجر:** عضوية store-scoped، مع سجل audit للقرارات، وعدم السماح بتعديل بيانات متجر آخر.
8. **إرسال المنتج للمراجعة:** التحقق من الفئة والحقول والصور والسعر/الوحدة، ثم موافقة قبل النشر.
9. **المراجعة المستمرة:** البلاغات والتحديثات والتعطيل/الاستئناف؛ ووقت آخر تحقق ظاهر للمستخدم.

لا تتطابق عملية SHEIN الأمريكية ذات متطلبات إيرادات ووثائق معينة مع السوق اليمني. على إب ماركت تحديد المطلوب بالحد الأدنى بعد مراجعة قانونية وتشغيلية محلية، وعدم جمع مستندات هوية قبل جاهزية الحماية وسياسة الاحتفاظ والحذف.

## 7. خطة تنفيذ مرتبة حسب الاعتماديات

### P0 / حواجز الثقة قبل أي إطلاق تجاري
- لا تسوّق الأسماء الـ 11,060 بوصفها 11,060 متجرًا موثقًا.
- تأكد من أن كل نص المستخدم يمر بترميز آمن، وأن الصور وروابطها لا تُحقن بشكل خطير.
- راجع مرجع `cloud-catalog.js` وحدد مصدره أو أزل الاعتماد غير المستخدم بعد اختبار.
- لا تضع أسرار API في الواجهة أو المستودع العام.
- حدد بوضوح ما هو محلي وما هو مشترك.

### المرحلة A — أساس البيانات والثقة (الأولوية الأعلى)
1. تحديد المستودع الخلفي/Worker الحقيقي وقراءته قبل كتابة كود جديد؛ توثيق ما إذا كانت قاعدة البيانات والتخزين موجودين أصلًا.
2. اختيار PostgreSQL أو backend مُدار مع صلاحيات دقيقة ونسخ احتياطي.
3. ترحيل الأسماء المستوردة إلى جدول منشآت بحقل `source=imported-name-only` و`verification_status=unverified`، مع مقارنة صفوف المصدر والوجهة وتسجيل نسخة الاستيراد.
4. حساب أسماء متشابهة مرشحة للتكرار وعرضها للمراجعة؛ لا تدمج الفروع آليًا.
5. تطوير تسجيل دخول وتفويض ومراجعة متجر وبلاغات.
6. تغيير تدفقات «أضف محليًا» إلى خدمة خادم حقيقية أو إبقاؤها محلية بوضوح؛ لا ادعاء نشر مشترك.
7. إجراء اختبار من جهازين: بعد موافقة سجل واحد، يظهر في الجهاز الثاني بالحالة الصحيحة؛ المستخدم غير المخوّل لا يستطيع تعديله.

**بوابة قبول المرحلة A:** قاعدة مشتركة، صلاحيات خادم، حالات توثيق صريحة، نسخ احتياطي قابل للاستعادة، ومسار موافقة قابل للتدقيق.

### المرحلة B — المتاجر والمنتجات
1. صفحات متجر عامة مستقلة بروابط قابلة للمشاركة.
2. إدارة عضويات التاجر وحالة البيع.
3. جداول منتجات ومتغيرات وعروض سعر ومخزون مع timestamp.
4. معالجة الصور وضغطها وتخزينها وتصنيفها بأمان.
5. مسار مسودة → مراجعة → منشور، مع سبب الرفض وإمكانية تعديل المسودة.
6. مراقبة البيانات المتقادمة، ومنع عرض سعر/توفر قديم على أنه مؤكد.
7. إعادة استخدام كتالوج مشترك للمنتج عند التطابق الحقيقي، مع بقاء السعر والمخزون مرتبطين بكل تاجر.

**بوابة القبول:** منتج أُضيف من حساب تاجر مخوّل يظهر علنًا بعد الموافقة، ويظهر في البحث، وتنعكس تحديثاته على جهاز آخر، ويرفض الخادم التعديل من حساب غير مخوّل.

### المرحلة C — البحث النصي
1. كتابة اختبارات استرجاع على عينة موثقة من أسماء إب.
2. إضافة حقول اسم بديل/حي/تصنيف.
3. إضافة مرادفات عربية ومحلية بمراجعة يدوية.
4. نتائج مرتبة ومقسمة إلى صفحات مع فلاتر قابلة للتفسير.
5. اختبار السرعة مع 11,060 اسمًا ثم مع كتالوج منتجات أكبر.
6. تقييم أثر تطبيع `ة → ه` على النتائج السلبية، وعدم اعتباره قاعدة صحيحة دائمًا.
7. إنشاء dashboard داخلي للبحث الفاشل، دون الاحتفاظ بنصوص حساسة أو معرّفات شخصية غير ضرورية.

**بوابة القبول:** اجتياز الاختبارات المتفق عليها للدقة وعدم النتائج الكاذبة والأداء على اتصال بطيء.

### المرحلة D — البحث بالصورة والمساعد
1. اختبار صورة معروفة مقابل المنتجات المعروفة.
2. إنشاء index للصور المعتمدة.
3. البحث المتجهي وإعادة الترتيب وإرجاع top-k.
4. اختبار الصور الضبابية والإضاءة السيئة والمنتج غير المتوفر والصورة التي لا تشبه أي منتج.
5. المساعد يستعلم من قاعدة بيانات منظمة ويعرض مصدر وتاريخ الأسعار والتوفر. لا يملك النموذج صلاحية تغيير بيانات أو قراءة مستندات خاصة.

**بوابة القبول:** نتائج قابلة للتكرار مع threshold واضح، فشل آمن، قياس جودة موثق وسياسة حذف للصورة.

### المرحلة E — الطلب والدفع والتوصيل
لا يبدأ هذا المسار قبل تأكيد توفر مزودي الدفع/المحافظ والتوصيل وقواعد التسوية والاسترجاع في اليمن. بعدها:
- order + order_items + order_events؛
- حجز المخزون بمعاملة ذرية؛
- idempotency لمنع الطلبات المكررة؛
- حالات دفع منفصلة عن حالات التوصيل؛
- إثبات التسليم وسياسة الإلغاء والاسترداد؛
- سجلات تسوية للتاجر ورسوم مفهومة؛
- اختبار نهاية إلى نهاية في بيئة اختبار قبل الطلبات الحقيقية.

## 9. ما يلزم للوصول إلى تقييم مرضٍ

### مقاييس المنتج
- نسبة السجلات التي تمت مراجعتها والتحقق من نشاطها، وليس حجم قائمة الأسماء فقط.
- دقة العناوين والإحداثيات والاتصال، ومعدل السجلات التي لها آخر تحديث حديث.
- معدل دمج التكرارات بعد مراجعة بشرية، مع حماية الفروع.
- Precision@5 / Recall@10 لمجموعة بحث عربية مرجعية.
- زمن استجابة البحث وواجهة المتجر على اتصال هاتف بطيء.
- معدل فشل الرفع والتسجيل والتحقق.
- زمن معالجة طلبات التاجر والبلاغات.
- معدل نجاح تدفق المنتج من مسودة إلى الموافقة إلى ظهوره على جهاز مختلف.

### تعريف «نتيجة مرضية»
يكون المشروع مرضيًا كـ **دليل مدينة موثوق** عندما يصبح السجل المشترك موثّق المصدر والحالة ويعمل البحث والخرائط والادعاء بالملكية على الخادم. ويصبح مرضيًا كـ **سوق إلكترونية** فقط عندما يعمل كتالوج منتجات وأسعار/مخزون محدثة، وصلاحيات التجار، والطلبات والتوصيل والدفع وفق متطلبات محلية، وتنجح اختبارات الأمان والأجهزة والشبكات.

## 10. ما تم تطبيقه على الفرع في هذه المراجعة

إضافةً إلى التقارير والمهارة، طُبق تحسين صغير فعلي في `index.html` على فرع التحليل:
- ترتيب نتائج البحث النصي الحالي ترتيبًا محددًا وقابلًا للتفسير: الاسم المطابق تمامًا أولًا، ثم الأسماء التي تبدأ بعبارة البحث، ثم بقية التطابقات الجزئية.
- الحفاظ على التطبيع العربي الموجود وعلى سلوك «عدم إظهار نتيجة» عند عدم وجود تطابق؛ لا تتم إضافة مرادفات غير موثقة ولا بيانات متاجر جديدة.
- إضافة اختبارات إلى `scripts/validate.mjs` تفحص ترتيب الدرجات، وعدم التطابق، وحالة تطبيع عربية عيّنة.

اختبار دخاني منفصل لمنطق ترتيب البحث في Node أعاد نتيجة نجاح، ودرجات العينة كانت: تطابق تام 1000، بادئة 800، تطابق جزئي 235، وعدم تطابق 0. **هذا لا يساوي تشغيل كامل `scripts/validate.mjs` على بيانات المستودع.** اجتاز `Jekyll site CI` المرتبط بالـ PR بناء الموقع بنجاح، لكنه لا يشغّل فاحص البيانات والبحث. لم يظهر تشغيل `Validate IBB Market` الذي يشغّل `scripts/validate.mjs`؛ إعداد التحقق الحالي يطلقه تلقائيًا عند الدفع إلى `main` أو عند تشغيل يدوي. لذلك لم أصف فحص المستودع الكامل بأنه ناجح. يلزم مراجعة التغيير وتشغيل التحقق الكامل قبل الدمج.

لم يتم تغيير قاعدة البيانات أو تفعيل مزايا تجارة غير موجودة؛ هذه الخطوة تحسين صغير على البحث بالاسم فقط، ولا تحول المشروع إلى سوق متعددة البائعين.

## 11. الخلاصة

- التحليل العام لـ SHEIN مفيد كمرجع لنظم التجارة، لكنه لا يكشف الخوارزميات الداخلية الخاصة ولا يثبت أن كل دولة لها نفس شروط البائع.
- إب ماركت لديه أساس واجهة وبيانات أسماء، مع شفافية جيدة حول كونها غير موثقة ومحلية في أجزاء مهمة.
- الفجوة الحرجة هي غياب البيانات المشتركة وحسابات وصلاحيات التاجر والتحقق والكتالوج الحقيقي، لا مجرد نقص شاشات أو تصميم.
- لا ينبغي بناء دفع وتسليم أو إعادة تفعيل البحث بالصورة قبل وجود الخدمات الخلفية والاختبارات الفعلية.
- التوصية: تنفيذ المراحل A ثم B ثم C، وبعدها D وE عند الجاهزية. لا تُعلن اكتمال منصة التجارة قبل اجتياز بوابات القبول الموضحة أعلاه.
